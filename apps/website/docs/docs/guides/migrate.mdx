# Move an existing setup into Tack

You may already keep skills in `~/.claude/skills`, commands in `~/.cursor/commands`, or a skill in a
repository's own `.claude/skills`. Each one then serves one agent, and a copy for another agent
drifts. Moving them into a Tack source keeps one copy of each, and Tack links it back into every
agent's folder.

Tack never moves or adopts a file it did not make. You move the folders yourself with `mv`, once;
Tack then links them back. This guide moves:

- two skills from `~/.claude/skills` and one command from `~/.cursor/commands`, which reached every
  project;
- the skill `app-conventions` from the repository `~/code/app`, which only that project used.

Leave Claude Code's own commands, in `~/.claude/commands` or a repository's `.claude/commands`,
where they are: Tack links no commands for Claude Code, so a command moved into a source would no
longer reach it. Turn one into a skill if you want Tack to manage it.

## 1. See what you have

`tack init` sets up Tack and lists what it found in the agents' user folders. It leaves those
entries where they are:

<Terminal commands={["tack init"]} output={initOutput} />

## 2. Move your files into a source

Create a folder for your source, ideally a Git repository you push somewhere, and move the skills
and commands into it:

```sh
mkdir -p ~/agent-setup/skills ~/agent-setup/commands
mv ~/.claude/skills/pr-review ~/.claude/skills/standup ~/agent-setup/skills/
mv ~/.cursor/commands/ship.md ~/agent-setup/commands/
```

A skill that sits in two agents' folders, such as `~/.claude/skills/pr-review` and
`~/.cursor/skills/pr-review`, moves once: keep the copy you trust and delete the other.

## 3. Register the source

<Terminal
  commands={["tack source add ~/agent-setup --skills skills --commands commands"]}
  output={sourceOutput}
/>

```sh
tack source add ~/agent-setup --skills skills --commands commands --apply
```

## 4. Link them back for every project

Skills in `~/.claude/skills` reached every project. In Tack that is a user pick: a skill is opt-in
at user level until you include it.

```sh
tack pick include pr-review --user
tack pick include standup --user
tack pick include ship --user
```

<Terminal commands={["tack sync --user"]} output={userSyncOutput} />

Cursor now gets the skills too, and Claude Code gets nothing for `ship`, because it takes no
commands. Apply it with `tack sync --user --apply`. The skills are back in `~/.claude/skills`, as
links:

<Terminal commands={["ls -l ~/.claude/skills"]} output={userLinksOutput} />

`ls` also lists the built-in skills Tack linked there.

To have a skill reach your user folders without a pick, set `user-activation: default` in its
metadata, as [Write a skill](./write-a-skill#3-choose-who-gets-it) shows.

## 5. Move a repository's own skill

A skill committed in a repository's `.claude/skills` serves only Claude Code. Registering the
project lists it, and leaves it where it is:

<Terminal commands={["tack project add app"]} output={projectAddOutput} />

Make the repository a source of its own. Move the skill to a folder no agent reads, such as
`.ai/skills`, with Git so its history follows:

```sh
mkdir -p .ai/skills
git mv .claude/skills/app-conventions .ai/skills/app-conventions
```

A skill with no metadata would reach every project that registers this source. Limit it to this
project with `metadata.tack` in its frontmatter, and keep the rest of the file:

```markdown
---
name: app-conventions
description: Follow this repository's naming, folder and test conventions when you change its code.
metadata:
  tack: |
    version: 1
    projects: [app]
---

# App conventions

Components live in `src/components`, one per file, with a test beside each.
```

Register the repository, from its root:

<Terminal commands={["tack source add . --skills .ai/skills"]} output={repoSourceOutput} />

Apply it with `tack source add . --skills .ai/skills --apply`, then sync the project. The skill
comes back in `.claude/skills` as a link, and Cursor gets it too; the user skills are not linked
twice:

<Terminal commands={["tack sync --project app"]} output={projectSyncOutput} />

Apply it with `tack sync --project app --apply`. Commit `tack.yaml` and `.ai/skills`, and ignore
the links: `tack status --project app --details` prints the `.gitignore` lines. Do not commit them,
even `.claude/skills/app-conventions -> ../../.ai/skills/app-conventions`, which stays inside the
repository: in a teammate's clone Tack did not make that link, so their sync reports it as a
`foreign-destination` conflict. Teammates then follow [Onboard a team](./team-onboarding), and
their own sync makes the same links.

## 6. Check

```sh
tack doctor
```

A skill left behind in an agent's folder under the same name as one you moved is reported as
`hand-made`: Tack keeps it and does not link over it. Delete the old copy and sync again.
