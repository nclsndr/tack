# Check health

Three commands tell you what state your setup is in. None of them changes anything.

| Command                     | Reads                                                            | Use it when                                  |
| --------------------------- | ---------------------------------------------------------------- | -------------------------------------------- |
| `tack doctor`               | The whole machine: state, agents, sources, projects, links, docs | You are not sure what is wrong               |
| `tack status --project app` | One project's links, or yours with `--user`                      | A skill is missing in one project            |
| `tack check ~/agent-setup`  | Files, without any state                                         | You edited a source, a profile or a document |

## The whole machine

`tack doctor` runs one check per area. Every problem ends with the command that fixes it. Here a
new skill, `write-changelog`, was written into a source but not synced yet:

<Terminal commands={["tack doctor"]} output={doctorOutput} />

A failed check exits with code `1`; warnings and skipped checks exit `0`. Doctor works before
`tack init` too, and then names it as the first step.

When a project's fixed profile holds a member an enabled agent cannot take, such as a command with
Claude Code enabled, the `profiles` check passes and names the skipped member in a note. See
[Share a fixed set with a profile](./profiles#when-an-agent-cannot-take-a-member).

One failure has no single command to run:

- **`profiles`, a member is unavailable.** A source the profile uses was removed. Registering it
  again is not enough, because the profile was applied with the old registration: register it, then
  apply the profile again with `--force`. Or apply a profile without those members.

## One project

`tack status` shows each link of one project that is not as `tack sync` would leave it, and the
command that fixes it. Run inside a project, it reads that project:

<Terminal commands={["tack status"]} output={statusOutput} />

`missing` means the link is not there yet. Other states you can meet:

| State                 | Meaning                                                                                        | What to do                                                       |
| --------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `missing`             | A selected resource has no link yet.                                                           | `tack sync --project app`, then `--apply`                        |
| `hand-made`           | A file or folder you made sits where Tack would link a skill of the same name. Tack leaves it. | Keep yours with `tack pick exclude`, or move yours away and sync |
| `unrecorded`          | The link Tack would write is there, but Tack has no record of it, as in a clone of a commit.   | `tack sync --project app --apply` adopts it                      |
| `foreign-destination` | Something Tack did not make, and not the link it would write, sits at a link's path.           | `git rm` it if it is committed, or move it away, then sync       |
| `managed-link-drift`  | A link Tack made was changed outside Tack.                                                     | Put it back with sync, or deselect the resource                  |
| `selection-collision` | Two sources give a selected resource the same name.                                            | `tack pick exclude SOURCE:NAME` for the one you do not want      |
| `dependency-blocked`  | A selected skill needs a skill that is excluded or missing.                                    | The diagnostic names the blocker and the step that lifts it      |

`tack status --project app --details` lists every link, what each agent gets and why, and the lines
for `.gitignore`.

## Before anyone uses it

`tack check` reads files only: a source folder, a profile, a bundle or a document. It needs no state
and runs no code, so it works in CI or before you register a source. It reports each problem by file
and line, and exits with code `1` on an error:

```sh
tack check ~/agent-setup
tack check ~/agent-setup ~/code/acme-agent-skills
tack check ~/agent-setup/handbook/on-call.md
```

Pass companion sources together when a profile names members from both.
[Write a skill](./write-a-skill#2-check-it) shows a failing check and its fix.

## After an upgrade

Run `tack init` after every Tack upgrade: it points the built-in skills at the new version and
changes nothing else. `tack upgrade` prints the command that upgrades Tack, for the way it was
installed.
